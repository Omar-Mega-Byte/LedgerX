LEDGERX — LIVING PROJECT CONTEXT
================================

Purpose
-------
LedgerX is a production-inspired Java/Spring backend portfolio project focused on financial correctness,
payments, digital wallets, immutable ledger design, concurrency, idempotency, event-driven processing,
reliable messaging, security, and auditability.

This file exists so Codex or any other coding assistant working inside the LedgerX project folder understands:
- the current product direction,
- the intended engineering depth,
- the important architectural concerns,
- the expected technology stack,
- the feature priorities,
- and how future changes should be handled.

IMPORTANT: NOTHING IN THIS FILE IS FINAL.
-----------------------------------------
This is a living technical context file, not a frozen specification.

The developer expects to change:
- service boundaries,
- package structure,
- APIs,
- database schemas,
- event names,
- security design,
- technologies,
- business rules,
- priorities,
- and feature scope.

Always prefer the newest explicit developer instruction over this document.

If new requirements conflict with this file:
1. Follow the new requirement.
2. Adapt the architecture coherently.
3. Update related code and tests.
4. Add migrations when persistence changes.
5. Update documentation when architecture materially changes.
6. Do not preserve an outdated design just because it appears here.

The goal is to build as much as possible in roughly one month, but quality and correctness matter more
than completing every feature.

ENGINEERING PHILOSOPHY
======================================================================

Prefer:
- correctness over feature count,
- explicit business rules,
- testable domain logic,
- a smaller complete system over many unfinished services,
- production-inspired patterns used for real reasons,
- explainable design choices.

Avoid:
- adding technologies only to impress,
- creating many microservices without meaningful boundaries,
- placing business logic in controllers,
- exposing JPA entities directly,
- hiding financial logic behind generic CRUD,
- relying only on application validation when database constraints can help,
- pretending external integrations are real when they are mocked.

Every difficult feature should ideally have:
- a clear purpose,
- tests,
- README documentation,
- failure-case handling,
- and an explanation of the design tradeoff.

======================================================================
CORE FEATURE — DOUBLE-ENTRY LEDGER
======================================================================

The strongest feature of LedgerX should be an immutable or append-only double-entry ledger.

Do not model important money movement only as:

wallet.balance = wallet.balance - amount

Instead, important financial movement should generate balanced ledger entries.

Example:

Transaction:
TX-92818

Entries:
USER_WALLET        -500 EGP
MERCHANT_WALLET    +490 EGP
PLATFORM_FEES       +10 EGP

Total:
0 EGP

Important rules:
- Every posted ledger transaction must balance.
- Entries should be append-only or immutable after posting.
- Corrections should preferably use compensating entries.
- Monetary values must never use float/double.
- Currency must be explicit where relevant.
- Financial history should be auditable.
- Ledger integrity should be testable.

Potential classes:
- LedgerAccount
- LedgerTransaction
- LedgerEntry
- Money
- Currency

Names can change.


======================================================================
BALANCE MODEL
======================================================================

Possible approaches:

A. Calculate balance from ledger entries.
B. Maintain a derived balance for performance.
C. Use both, with the ledger as the ultimate source of truth.

Do not freeze the design yet.

If a cached/derived balance exists:
- update it safely,
- protect concurrent modifications,
- reconcile it with the ledger,
- and document which store is authoritative.

PAYMENTS
======================================================================

Potential payment states:
- CREATED
- AUTHORIZED
- PROCESSING
- COMPLETED
- FAILED
- CANCELLED
- REFUND_PENDING
- PARTIALLY_REFUNDED
- REFUNDED

Use explicit valid transitions.

Example:
CREATED -> AUTHORIZED
AUTHORIZED -> PROCESSING
PROCESSING -> COMPLETED
PROCESSING -> FAILED
COMPLETED -> REFUND_PENDING
REFUND_PENDING -> REFUNDED

Invalid transitions must be rejected.

Avoid generic "setStatus()" behavior from controllers.


======================================================================
IDEMPOTENCY
======================================================================

High-priority feature.

Example:
POST /api/v1/payments

Header:
Idempotency-Key: <client-generated-key>

Repeated requests with the same key must not create repeated financial effects.

Need to consider:
- same key + same payload
- same key + different payload
- concurrent requests using same key
- expiration
- merchant/user scope
- response replay
- transaction boundaries
- request fingerprint/hash

Potential storage:
- PostgreSQL
- Redis with durable backing
- dedicated idempotency table

The first implementation should prefer correctness and simplicity.


======================================================================

======================================================================

High-value reliability feature.

Problem:
Database state and Kafka publication must not become inconsistent.

Preferred concept:

  insert outbox event

Possible outbox fields:
- id
- aggregate_type
- aggregate_id
- event_type
- payload
- created_at
- published_at
- status
- retry_count

Initial implementation may use polling.

Possible later evolution:
- Debezium CDC

IDEMPOTENT CONSUMERS
======================================================================

Kafka consumers must assume duplicate delivery can happen.

Possible strategy:
processed_events table

Fields:
- event_id
- consumer_name
- processed_at

Goal:
At-least-once transport with effectively-once business behavior where needed.

A repeated PAYMENT_COMPLETED event must not:
- duplicate notifications,
- duplicate fees,
- duplicate downstream business side effects.


======================================================================
CONCURRENCY
======================================================================

Important interview area.

Potential races:
- two transfers spend the same balance,
- duplicate payment requests arrive together,
- two refunds are requested simultaneously,
- the same wallet is updated concurrently.

Potential techniques:
- optimistic locking with @Version
- pessimistic locking
- atomic SQL updates
- database constraints
- stronger transaction isolation
- Redis locks only where truly justified

Do not use distributed locks automatically.

Choose based on the real race condition and document why.

======================================================================
RISK / FRAUD ENGINE
======================================================================

No machine learning is required.

A rule-based system is enough.

Possible signals:
- payment velocity
- abnormal amount
- repeated failures
- new device
- suspicious IP
- geography
- account age
- merchant-specific settings

Possible result:
- ALLOW
- REVIEW
- BLOCK

Example scoring:
+30 too many recent attempts
+20 new device
+40 high amount
+50 risky location

Thresholds are only examples and should remain configurable.

DATABASE RULES
======================================================================

Use:
- PostgreSQL
- Flyway
- constraints
- indexes
- proper transaction boundaries
- pagination
- explicit relationships
- intentional fetch plans

- ddl-auto=create for production-like usage

- EAGER everywhere

- positive monetary amounts
- valid references
- unique API key identifiers

RETRY / RESILIENCE
======================================================================

Retry only transient failures.

Potential retryable:
- network errors
- 503 responses
- webhook timeouts
- temporary Kafka failures

Potential non-retryable:
- invalid state
- unauthorized operation
- invalid payload
- insufficient funds

Use:
- max attempts
- exponential backoff
- dead-letter handling where relevant
- metrics around retries

Avoid infinite retries.
